# Extension phase-boundary audit and recovery

The extension executed 48/113 new 2D trials (131 adapter intents) before a shared-load stop at 23.401/24. The pool closed and published its 48 rows. The next 3D pool was refused before its directory or any 3D attempt existed; the release-level COMPLETE ledger was therefore absent. Both the monitor and publication observer stopped for audit, as designed for an unclassified incomplete release. The automation did not finish the campaign: all failures and original logs remain preserved.

`recover_phase_boundary.py` audits the stopped process identity, frozen selection/jobs, all 460 published 2D attempt identities and query journals, closed pool/no reservations, and measured reaped child/supervisor CPU. It refuses recovery if any 3D pool could have started. It creates a new metadata-only release, preserving the original partial archive and every UNKNOWN result. The original 414/525 3D rows are carried forward unchanged. No model, teacher, TEST selection or physical outcome is changed; no episode is retried.

The final controller CPU could not be recovered. Rather than infer an exact measurement, the recovery charges its full elapsed upper interval (441.118397 seconds) across all 22 permitted logical CPUs. After subtracting already-accounted coordinator CPU, this adds 9573.638535 conservative CPU seconds. Exact new physical-child CPU is 1195.443260 seconds and exact supervisor CPU is 89.339710 seconds. The corrected 2D charged CPU is 21709.455215 seconds, still within the explicitly approved prior-use-plus-43200 ceiling. This loose bound is not actual CPU consumption. The audit JSON contains source hashes and the full derivation. Recovery itself dispatches zero physical queries.

The source fix converts only a resource refusal before a pool directory exists into a zero-attempt phase ledger. It retains all jobs as unattempted and records actual coordinator overhead. Refusals/errors after dispatch continue to require audit. This lets the ordinary supervisor see a clean phase boundary and resume after headroom recovery. Prior conservative CPU-accounting labels are preserved in later merged ledgers; final reports carry the recovery proof explicitly.

The remaining 65 approved 2D identities may execute under the existing approval, with prior 48 attempts and 131 calls charged and retained. Three workers and CPU affinity 0–21 remain. The shared teacher, query/trial caps, 4 GiB pool RAM, cumulative disk guard and global 5523-call ceiling are unchanged. Original 3D CPU remains limited to 21600 seconds; any unexecuted 3D identities remain NOT_RUN.
